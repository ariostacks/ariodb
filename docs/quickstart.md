# Quickstart

This page gets you from nothing to a working ariodb in two ways. First, the
demo script, which sets everything up for you in a couple of minutes.
Second, a complete setup by hand against a local Postgres in Docker:
database roles, the config file, secrets, preparing the database, running
ariodb, and then watching it refuse a statement, roll back a write, hold a
read for approval and undo an agent's session. It is for anyone evaluating
ariodb or about to deploy it; the hand-built setup is the same shape as a
production one.

You need Docker, Rust and `psql`. See [installation](installation.md) for
the build requirements.

## The demo

```bash
./scripts/demo.sh
```

[`scripts/demo.sh`](../scripts/demo.sh) does the following, and undoes it
when you press Ctrl-C:

1. Builds ariodb (`cargo build`).
2. Starts Postgres 16 in Docker (container `ariodb-demo-pg`, on
   `127.0.0.1:55440`) with `wal_level = logical`.
3. Creates three tables: `customers` (50 rows), `orders` (1,000 rows,
   cascading from `customers`) and `secrets`, and a gateway role,
   `ariodb_gw`.
4. Writes a config to `.ariodb-demo/ariodb.toml`: one `read_write` agent,
   `coding-agent`, allowed `orders` and `customers`, with a row limit of
   200; a dashboard approver; a rule that holds reads of customer emails
   for approval; a rule that refuses functions that read server files.
5. Runs `ariodb setup`, sets the dashboard password and starts
   `ariodb serve`.
6. Sends some good and bad agent statements, so the dashboard has something
   to show: a count, a three-row update, a delete that cascades, a
   `DELETE` without `WHERE`, a 599-row update, `pg_read_file`, a read of
   `secrets`, and a read of customer emails that waits for approval.

The sample statements run through a `postgres:16` container that reaches
ariodb at `host.docker.internal`, which Docker Desktop provides. On Linux
without it, they fail quietly; run them yourself instead.

Then connect as the agent and open the dashboard:

```bash
psql "postgres://coding-agent:demo-agent-token@127.0.0.1:6543/app?sslmode=disable"
```

The dashboard is at <http://127.0.0.1:8080> (user `root`, password
`demo-dashboard-password`). Try:

- `DELETE FROM orders`: refused, because it has no `WHERE`.
- `UPDATE orders SET status = 'void' WHERE id < 600`: runs, is measured at
  599 rows, and is rolled back because the limit is 200.
- `SELECT name, email FROM customers`: waits until you approve it on the
  dashboard's Approvals page.

The demo needs ports 55440, 6543 and 8080 free. Every password in it is a
throwaway test value.

## A real setup, step by step

The rest of this page builds the same kind of setup by hand, the way you
would for a real database, so you can see every moving part. It uses
Postgres 17 in Docker on port 55432 and three database roles:

| Role | Used for | Needs |
|---|---|---|
| `ariodb_gw` | The gateway login: agents' queries run as this | Only the grants agents need |
| `ariodb_journal` | Reading the change stream for the journal | `REPLICATION` |
| `ariodb_reader` | An optional read-only credential for one agent | `SELECT` on its tables |

The tables belong to `postgres`, as they would belong to your application's
owner role in production. `ariodb setup` is run once as that owner, because
only a table's owner can change its replica identity and publish it.

### 1. Start Postgres with logical replication

```bash
docker run -d --name ariodb-pg \
  -e POSTGRES_PASSWORD=not-a-real-admin-password \
  -e POSTGRES_DB=app \
  -p 127.0.0.1:55432:5432 \
  postgres:17 -c wal_level=logical

# Wait for the real server (the image starts a temporary one first).
until docker exec ariodb-pg pg_isready -h 127.0.0.1 -U postgres -d app >/dev/null 2>&1; do sleep 1; done
```

`wal_level = logical` is what lets ariodb read every committed change for
undo. On a managed service it is usually a setting called "logical
replication" or "logical decoding"; see [compatibility](compatibility.md).

### 2. Create the tables and roles

```bash
docker exec -i ariodb-pg psql -v ON_ERROR_STOP=1 -U postgres -d app <<'SQL'
-- Application tables, owned by postgres.
CREATE TABLE customers (
  id    int PRIMARY KEY,
  name  text NOT NULL,
  email text
);
CREATE TABLE orders (
  id          int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id int NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  status      text NOT NULL,
  total       numeric(10,2) NOT NULL
);
CREATE TABLE payroll (id int PRIMARY KEY, employee text, salary numeric);

INSERT INTO customers
  SELECT g, 'Customer ' || g, 'c' || g || '@example.test' FROM generate_series(1, 50) g;
INSERT INTO orders (customer_id, status, total)
  SELECT 1 + (g % 50), 'paid', (g % 97) + 0.99 FROM generate_series(1, 1000) g;

-- The gateway login: what agents' queries run as. Only what agents need:
-- no superuser, no REPLICATION, nothing on payroll.
CREATE ROLE ariodb_gw LOGIN PASSWORD 'not-a-real-password';
GRANT USAGE ON SCHEMA public TO ariodb_gw;
GRANT SELECT, INSERT, UPDATE, DELETE ON customers, orders TO ariodb_gw;
GRANT USAGE ON SEQUENCE orders_id_seq TO ariodb_gw;

-- The journal login: reads the change stream through a replication slot.
CREATE ROLE ariodb_journal LOGIN REPLICATION PASSWORD 'not-a-real-journal-password';

-- An optional read-only credential, for an agent that should never write
-- even if ariodb were misconfigured.
CREATE ROLE ariodb_reader LOGIN PASSWORD 'not-a-real-reader-password';
GRANT USAGE ON SCHEMA public TO ariodb_reader;
GRANT SELECT ON orders TO ariodb_reader;
SQL
```

Why these grants:

- The **gateway role's grants are the real boundary**. ariodb checks which
  tables a statement names, but a view or function the role may use can
  reach further. `payroll` is deliberately not granted, so even a mistake in
  ariodb's config could not expose it.
- Undo runs as the gateway role here (it can select, insert, update and
  delete the protected tables). In production you may prefer a separate
  undo login in `ARIODB_ADMIN_URL`.
- The journal role needs `REPLICATION` and nothing else once the database
  is set up.

[Postgres](postgres.md) covers the roles in more depth.

### 3. Make a working directory and put ariodb on the path

```bash
cd /path/to/ariodb && cargo build --release
export PATH="$PWD/target/release:$PATH"
mkdir -p ~/ariodb-quickstart && cd ~/ariodb-quickstart
```

ariodb reads `ariodb.toml` from the current directory by default, and the
state directory in this config is relative to it, so run every command
below from `~/ariodb-quickstart`.

### 4. Write `ariodb.toml`

```toml
# ariodb quickstart config. No passwords in this file: they come from the
# environment and the encrypted secret store.

[database]
# The gateway login agents' queries run as. ARIODB_DATABASE_URL, which
# carries the password, wins over this line.
url = "postgres://ariodb_gw@127.0.0.1:55432/app"

[limits]
max_rows_per_write = 100      # a write that changes more rows is rolled back
statement_timeout_ms = 5000

[proxy]
listen = "127.0.0.1:6543"     # where agents connect

[journal]
enabled = true
dir = ".ariodb"               # state directory, relative to where you run ariodb

[[agents]]
name = "coding-agent"
access = "read_write"
tables = ["orders", "customers"]
token_env = "ARIODB_TOKEN_CODING_AGENT"

[[agents]]
name = "support-bot"
access = "read_only"
tables = ["orders"]
token_secret = "support-bot-token"
credential = "reader"         # runs as ariodb_reader, not the gateway login

[[credentials]]
name = "reader"
secret = "reader-url"

[[approvers]]
name = "ops"
type = "dashboard"

[[rules]]
name = "no-file-functions"
# Matches pg_read_file and pg_catalog.pg_read_file alike.
condition = "sql.functions.exists(f, f.matches('(^|[.])pg_(read_file|read_binary_file|ls_dir|stat_file)$'))"
verdict = "deny"
reason = "functions that read server files are off-limits"

[[rules]]
name = "customer-emails-need-a-human"
condition = "sql.kind == 'read' && 'customers' in sql.tables && sql.statement.contains('email')"
verdict = "approve"
approve = ["ops"]
reason = "reading customer emails needs a person to agree"

[[rules]]
name = "big-writes-need-a-human"
stage = "after"
condition = "effects.rows > 20"
verdict = "approve"
approve = ["ops"]
agents = ["coding-agent"]
reason = "changing more than 20 rows at once needs a person to agree"

[approvals]
timeout_seconds = 120

[dashboard]
listen = "127.0.0.1:8080"
public_url = "http://127.0.0.1:8080"
config_writes = false
```

What this sets up:

- `coding-agent` may read and write `orders` and `customers`. Every write
  is measured before commit and rolled back above 100 rows. Writes of 21
  to 100 rows wait for a person (the after-stage rule).
- `support-bot` may only read `orders`, and runs as `ariodb_reader`, so the
  database would refuse its writes too.
- Reads that mention customer emails wait for a person; functions that read
  server files are refused for everyone.
- Every other table, including `payroll`, is refused by the built-in policy
  because no agent lists it.

The [configuration reference](configuration.md) covers every option, and
[rules](rules.md) the CEL conditions.

### 5. Store the secrets

Database URLs and tokens never go in the config file. This setup uses both
places ariodb can read them from. First, environment variables, kept in a
file you can source in each terminal:

```bash
cat > quickstart.env <<'EOF'
export ARIODB_DATABASE_URL='postgres://ariodb_gw:not-a-real-password@127.0.0.1:55432/app'
export ARIODB_JOURNAL_URL='postgres://ariodb_journal:not-a-real-journal-password@127.0.0.1:55432/app'
export ARIODB_TOKEN_CODING_AGENT='agent-token-local-test-only'
EOF
chmod 600 quickstart.env
. ./quickstart.env
```

Then the encrypted secret store, for the second agent's token and the
reader's URL:

```bash
printf '%s\n' 'agent-token-support-local-test-only' | ariodb secret set support-bot-token
printf '%s\n' 'postgres://ariodb_reader:not-a-real-reader-password@127.0.0.1:55432/app' | ariodb secret set reader-url
ariodb secret list
```

```text
stored secret 'support-bot-token'
stored secret 'reader-url'
reader-url
support-bot-token
```

The store lives in the state directory (`.ariodb/secrets.json`), sealed
with a key in `.ariodb/master.key` unless you set `ARIODB_MASTER_KEY`.
`ariodb secret set` reads the value from stdin; with real secrets, use
`read -rs V && printf '%s\n' "$V" | ariodb secret set <name>` so the value
stays out of your shell history. In production, generate tokens with
`openssl rand -hex 32`.

### 6. Check the config

```bash
ariodb check
```

```text
database      postgres://ariodb_gw:***@127.0.0.1:55432/app
row limit     100 rows per write
timeout       5000 ms
proxy         127.0.0.1:6543
journal       .ariodb
if checks fail, refuse the statement (fail closed)

agent coding-agent     read and write  token set  orders, customers
agent support-bot      read only       token set  orders
```

`check` parses the file, compiles the rules and checks that agents,
credentials, approvers and tunnels refer to things that exist. It does not
connect to the database. `token set` confirms each agent's token was found;
`no token` would mean that agent cannot log in.

You can already ask how ariodb would judge a statement, without a database:

```bash
ariodb explain --agent coding-agent "DELETE FROM orders"
ariodb explain --agent coding-agent "SELECT name, email FROM customers LIMIT 3"
ariodb explain --agent support-bot "UPDATE orders SET status = 'void' WHERE id = 1"
```

```text
deny  (decided by: policy)  destructive statements are never allowed for agents: DELETE without WHERE removes every row
approve  (decided by: customer-emails-need-a-human)  reading customer emails needs a person to agree
deny  (decided by: policy)  agent 'support-bot' is read only
```

`explain` judges the built-in policy and before-stage rules only. It cannot
predict the row count of a write; that needs the write to run.

### 7. Ask the database what works: `ariodb doctor`

```bash
ariodb doctor
```

`doctor` connects with each login and checks what this database supports.
Every check is read-only or runs in a transaction that is rolled back.
Before `setup`, the journal checks fail, and `doctor` exits with status 1:

```text
default login: ariodb_gw@127.0.0.1:55432/app
  ok    connected (no TLS, local database)
  ok    PostgreSQL 17.6 (Debian 17.6-1.pgdg13+1)
  ok    reads run in READ ONLY transactions, and the database enforces them
  ok    writes are measured before commit (a 3-row test write counted 3)
  ok    writes can be tagged with their session for the journal
  ok    every agent table exists and this login can use it

credential 'reader': ariodb_reader@127.0.0.1:55432/app
  ok    connected (no TLS, local database)
  ok    reads run in READ ONLY transactions, and the database enforces them
  ok    writes are measured before commit (a 3-row test write counted 3)
  ok    writes can be tagged with their session for the journal
  ok    every agent table exists and this login can use it

journal: ariodb_journal@127.0.0.1:55432/app
  ok    wal_level is logical
  FAIL  replication slot 'ariodb' does not exist; run `ariodb setup`
  FAIL  publication 'ariodb' does not exist; run `ariodb setup`
  FAIL  tables without full before-images (REPLICA IDENTITY FULL): customers, orders; run `ariodb setup` again

what works here
  yes  reads, forced read-only
  yes  writes, checked before commit
  no   undo of agent sessions: not set up (run ariodb setup)
error: some checks failed
```

The version line will match your image. Reads and checked writes already
work; undo needs the next step.

### 8. Prepare the database: `ariodb setup`

`setup` sets `REPLICA IDENTITY FULL` on every protected table (so changes
carry full before-images), creates a publication listing them, and creates
the logical replication slot. Run it once, as the tables' owner, by
overriding `ARIODB_JOURNAL_URL` for this one command:

```bash
ARIODB_JOURNAL_URL='postgres://postgres:not-a-real-admin-password@127.0.0.1:55432/app' ariodb setup
```

```text
ok   wal_level is logical
ok   customers: changes will carry full before-images
ok   orders: changes will carry full before-images
ok   publication 'ariodb' covers customers, orders
ok   replication slot 'ariodb' is ready
```

`setup` is safe to run again, and you should run it again whenever you give
an agent write access to another table. Run `ariodb doctor` once more: the
journal section now ends with `the change stream can be read, with session
tags`, and all three lines under `what works here` say `yes`.

### 9. Set a dashboard password

```bash
printf '%s\n' 'not-a-real-dashboard-password' | ariodb dashboard-password
```

```text
password set for 'root'
```

The first user is `root`. Passwords need at least 12 characters.

### 10. Run ariodb

In a second terminal, from the same directory:

```bash
cd ~/ariodb-quickstart && . ./quickstart.env
ariodb serve
```

```text
ariodb: agents can connect to postgres://<agent>@127.0.0.1:6543
ariodb: dashboard at http://127.0.0.1:8080
ariodb: journal is recording changes to .ariodb/journal.jsonl
ariodb: reads yes; checked writes yes; undo yes
```

The lines may come in a different order. Leave it running.

### 11. Connect as the agent

Back in the first terminal, connect with `psql` as `coding-agent`, with its
token as the password:

```bash
PGPASSWORD="$ARIODB_TOKEN_CODING_AGENT" psql "postgres://coding-agent@127.0.0.1:6543/app?sslmode=disable"
```

`sslmode=disable` is only because this local setup has no TLS on the
proxy. Anywhere else, give the proxy a certificate and set
`require_tls = true`: agents send their tokens as passwords.

A read works as normal:

```text
app=> SELECT count(*) FROM orders;
 count
-------
  1000
(1 row)
```

### 12. See a refusal

```text
app=> DELETE FROM orders;
ERROR:  ariodb: destructive statements are never allowed for agents: DELETE without WHERE removes every row
app=> SELECT * FROM payroll;
ERROR:  ariodb: agent 'coding-agent' may not use table 'payroll'
app=> SELECT pg_read_file('/etc/passwd');
ERROR:  ariodb: functions that read server files are off-limits
```

None of these reached the database. The first two were refused by the
built-in policy, the third by the `no-file-functions` rule.

### 13. See a write rolled back

```text
app=> UPDATE orders SET status = 'void' WHERE id < 600;
ERROR:  ariodb: rolled back: the statement would change 599 rows (599 orders); the limit is 100
```

This one did reach the database. ariodb ran it inside a transaction,
measured that it changed 599 rows, and rolled it back before commit. The
agent never saw `UPDATE 599`. Had a trigger or cascade changed another
table the agent may not change, that would have been caught the same way.

A small write goes through:

```text
app=> UPDATE orders SET status = 'refunded' WHERE id IN (5, 6, 7);
UPDATE 3
```

### 14. Approve a statement in the dashboard

```text
app=> SELECT name, email FROM customers LIMIT 3;
```

`psql` waits: the `customer-emails-need-a-human` rule is holding the
statement for the `ops` approver. Open <http://127.0.0.1:8080>, sign in as
`root`, and go to **Approvals**. The request shows the agent, the SQL and
the rule. Click **Approve**, and the rows appear in `psql`:

```text
    name    |      email
------------+-----------------
 Customer 1 | c1@example.test
 Customer 2 | c2@example.test
 Customer 3 | c3@example.test
(3 rows)
```

Nothing reached the database while the statement waited. Had you clicked
**Deny**, or let 120 seconds pass, the agent would have received an error
instead. You can also decide from the command line:

```bash
ariodb approvals            # pending requests, with their ids
ariodb approve a-7d2e90b1c4f5 --note "checked with support"
```

Quit `psql` (`\q`). The **Decisions** page now lists every statement you
sent, with its verdict and the rule that decided it.

### 15. Find the session and undo it

```bash
ariodb sessions
```

```text
session        agent              txns   rows  status     tables
s-3f9c2a71d0   coding-agent          1      3             orders
```

Only sessions that changed data are listed, so this is the `psql` session
with the three-row update; the rolled-back update never committed. Your
session id will differ. Look at the undo plan first:

```bash
ariodb undo --session s-3f9c2a71d0
```

```text
undo plan for s-3f9c2a71d0: 3 steps
  restore public.orders row (5)
  restore public.orders row (6)
  restore public.orders row (7)

nothing changed. Run again with --apply to undo.
```

Then apply it:

```bash
ariodb undo --session s-3f9c2a71d0 --apply
```

The plan is printed again, followed by:

```text
undone: 3 rows restored in one transaction
```

Orders 5, 6 and 7 are `paid` again, and `ariodb sessions` now shows the
session as `undone`. Undoing it a second time is refused. If anyone else
had changed those rows after the agent did, undo would have reported them
as conflicts and changed nothing (or, with `--skip-conflicts`, restored
only the others). You can do the same from the dashboard's
**Sessions and undo** page. [Undo](undo.md) explains the rules.

Finally, check the decisions log has not been edited:

```bash
ariodb audit
```

The output ends with `decisions log intact: N entries checked`.

### 16. Clean up

Stop `ariodb serve` with Ctrl-C, then:

```bash
docker rm -f ariodb-pg
rm -rf ~/ariodb-quickstart
```

Removing the container removes the replication slot with it. Against a
database you keep, drop the slot if you stop using ariodb
(`SELECT pg_drop_replication_slot('ariodb')`), or Postgres will keep WAL
for it indefinitely.

## Where to go from here

- Try `UPDATE orders SET status = 'shipped' WHERE id BETWEEN 100 AND 129`:
  30 rows is under the limit but over the after-stage rule's 20, so it
  waits for approval with its transaction open, then commits or rolls back.
- Connect as `support-bot` (token `agent-token-support-local-test-only`)
  and try a write.
- Give an agent ariodb as an MCP tool instead of a database connection:
  `ARIODB_AGENT_TOKEN="$ARIODB_TOKEN_CODING_AGENT" ariodb mcp --agent coding-agent`.
  See [MCP](mcp.md).
